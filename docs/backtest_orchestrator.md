# Backtest Orchestrator: Internal Mechanics

The `backtest-orchestrator` is a Python CLI tool (`orchestrator.py`) designed to act as the strict referee of the backtest. Its primary mandate is to prevent data leakage and guarantee that both the classical and quantum solvers are judged fairly on cryptographically identical inputs.

## The Problem It Solves
If solvers were allowed to fetch their own data or compute their own covariance matrices, subtle bugs or numerical differences in how they parse the data could lead to variations in the inputs. The backtest would no longer be comparing "Quantum vs Classical", it would be comparing "Parser A vs Parser B". 

The Orchestrator centralizes input generation to eliminate this variable.

---

## Detailed Step-by-Step Execution Flow

When triggered via `docker compose run --rm backtest-orchestrator`, the script executes the following sequential steps:

### 1. Initialization and Date Boundaries
*   Connects to the `results.db` SQLite database using `sqlite3`.
*   Reads the `BACKTEST_START_DATE` and `BACKTEST_END_DATE` from environment variables.
*   Loads the `daily_returns.csv` (generated by the `data_loader`) into a Pandas DataFrame.
*   Filters the DataFrame index to find all valid "Rebalance Dates" (typically every Friday) that fall within the boundary.

### 2. The Rebalance Loop
For each Rebalance Date in the series, the Orchestrator initiates a strict sequence:

#### A. Data Preparation (The Lookback Window)
*   It looks backward $T$ days (`BACKTEST_WINDOW_DAYS`, e.g., 252 trading days representing 1 year) from the current Rebalance Date.
*   It extracts the return slice for that exact window.
*   It passes this slice to the `data_loader` pure functions:
    *   `sigma_for_date()`: Computes the empirical covariance matrix $\Sigma$ of the assets over the window, utilizing Ledoit-Wolf shrinkage.
    *   `caps_for_date()`: Computes the maximum allowable weight per asset based on an inverse-volatility heuristic.
    *   `get_mu_hat()`: Retrieves the expected returns $\hat{\mu}$ vector (currently a placeholder zero-vector as we focus on minimum-variance/risk).

#### B. Request Locking & Hashing
*   The orchestrator instantiates an `OptimizationRequest` Pydantic model containing the $\hat{\mu}$, $\Sigma$, caps, and risk aversion $q$.
*   It generates a deterministic SHA-256 hash of the $\Sigma$ matrix and the caps array.
*   It creates a unique `request_id` for this specific date (e.g., `reb-20240105-8278c27e`).

#### C. Concurrent Dispatch
*   Using `httpx.Client`, the orchestrator serializes the *exact same* `OptimizationRequest` object to JSON.
*   It sends an HTTP POST request to `http://markowitz-service:8000/optimize`.
*   It sends an HTTP POST request to `http://qaoa-service:8000/optimize`.
*   It records the time it takes for each network request to return, logging the `solve_time_ms`.

#### D. Performance Evaluation (The Forward Look)
*   Once both solvers return their `OptimizationResult` JSON containing the chosen weights $w$, the orchestrator steps *forward* one week to the *next* Rebalance Date.
*   It extracts the actual, realized market returns of the assets over that forward week.
*   It computes the dot product of the chosen weights $w$ against the realized returns to find the gross portfolio return.

#### E. Turnover and Transaction Costs
*   The orchestrator retrieves the weights chosen by the solver in the *previous* week.
*   It calculates the absolute difference between the previous weights and the newly proposed weights $w$ to find the portfolio turnover.
*   It applies a transaction cost penalty (`BACKTEST_TCOST_BPS`, e.g., 10 basis points) to the turnover amount and deducts it from the gross portfolio return to find the **net realized return**.

#### F. Commit to Ledger
*   The orchestrator executes an `INSERT INTO` SQL command, writing the `request_id`, date, arm name, weights, net return, turnover, solve time, and hashes into the `results_store`.

### 3. Completion
Once the loop reaches the `BACKTEST_END_DATE`, the script terminates cleanly. The SQLite database is now fully populated and acts as the single source of truth for the `results-api` and Frontend Dashboard.
